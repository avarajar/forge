Change nothing and everything stays the same: every account has a default harness, and today that is Claude Code. What's new is a selector in the form, a badge on every session, and CW remembering which harness each session started with.

2 · Where the decision lives

Three levels, from the most general to the most specific. The lower one wins. If you set none, it is Claude Code, same as today.

Level 1

Account

Every account has a default harness, set when the account is created. The work account can be Claude and personal can be Codex.

cw account add personal --harness codex
Level 2

Project

A project can force a harness different from its account's. Useful when a repo works better with one.

cw project register ~/x --harness pi
Level 3

This task

What you pick in the Forge form, or the flag in the terminal. Applies to that session only.

cw work app SEI-214 --harness codex

3 · What happens when you click Start with Codex

Forge

Sends the choice to the server

The same POST as today with one more field.

POST /api/cw/start
{ "project": "seimseim-reservas", "task": "SEI-214", "harness": "codex" }
Forge · PTY

Opens the terminal and runs CW

cw work seimseim-reservas SEI-214 --harness codex
CW

Prepares the worktree and the context

Creates the worktree at .tasks/SEI-214 and links the .env files. If LINEAR_API_KEY is set, it fetches the Linear ticket and writes it into TASK_NOTES.md; otherwise Codex starts without it, because it has no MCP.

CW · driver

Hands off to the Codex driver

A small file knows how to start Codex, where its credentials live and what it supports. Codex starts already inside the worktree.

lib/harnesses/codex.sh
CODEX_HOME=~/.cw/accounts/work/codex codex "$(cat init_prompt.txt)"
CW · session

Remembers what it started with

When you resume, even from the terminal with no flags, it reopens Codex.

~/.cw/sessions/seimseim-reservas/task-SEI-214/session.json
{ "status": "active", "opens": 1, "harness": "codex" }
Forge

Reads the field and draws the badge

The Codex session shows up next to the Claude ones, in the same list and the same tabs.

5 · What stays the same and what changes

SituationBehavior
You start a task without picking a harnessSame as today: Claude Code
Sessions that already exist in ~/.cw/sessionsSame: no harness field means Claude Code
You resume a sessionOpens with the harness it was created with, even without flags
Account whose default is not ClaudeThe selector starts on that harness. You can change it for a single task
Harness not installed on the machineShown disabled in the selector with the reason. Never fails at start
Hooks, skip permissions, agent teamsOnly shown and applied when the harness supports them, which today means Claude Code
Loop taskClaude Code only: /loop is one of its commands. The selector disables the other harnesses
A Linear, GitHub or Notion ticket as the taskCW writes it into TASK_NOTES.md before launching, for any harness. GitHub always, through gh; Linear and Notion only with LINEAR_API_KEY / NOTION_TOKEN. Without a token only Claude Code reads it, through MCP

Connect on Claude Code, Pi or OpenCode: visible terminal

None of them has a login cw can drive without a screen. Forge opens a tab with the terminal and you finish the login there, including the API key for an OpenCode provider.

$ cw account login personal --harness claude
# the harness's own login screen continues here

While the tab is open, the cell reads Connecting… and Forge checks every 3 s.

Add account

Create an account

Name, default harness and, when that harness accepts providers, provider and model. The default harness cannot be changed later: cw has no account set.

cw account add glm --harness opencode --provider zai --model glm-5.1
Limit

Forge on another host

Browser login redirects to localhost on the machine running the harness. If you open Forge from another computer, only the Codex code works, and the screen says so above the matrix.
